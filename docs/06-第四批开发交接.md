## 一、本批修复清单（按问题归类）

### 1.1 车次绑定与表单

| 问题 | 根因 | 处理 | 文件 |
|---|---|---|---|
| 填了到达时间，重新进入发现被改掉 | `resolveArrivalTs` 对手动输入调用 `clampDuration`，强制夹在 30 分钟 ~ 24 小时之间，长途车（如 Z264 广州-拉萨 55 小时）直接被截断 | 手动输入**原样采用**，不再 clamp；`clampDuration` 只保留给按车次估算 | `utils/train.js`、`test/train.test.js` |
| 修改绑定 / 解除绑定点了没反应，且输入框仍可编辑 | 用了 `await wx.showModal(...)`，部分基础库不返回 `{confirm}` 结构，`res.confirm` 抛异常后静默失败 | 改回调式 Promise 包装；新增 `editing` 状态机，未进入编辑态时输入框 `disabled` | `pages/train-binding/*` |

### 1.2 帖子可见性（重要产品决策）

| 问题 | 根因 | 处理 |
|---|---|---|
| 各账号互相看不到帖子，无法验证接单 | 第三批 P0 第 7 项把匹配条件写成「同车次 **且** 同车厢」，不同车厢完全不可见 | 改为**只按车次匹配**。产品理由：同一列车上走几节车厢就能帮上忙，车厢号只是「我在哪」的定位信息，不构成可见性条件 |

> 这一步走了两次：先改成「同车厢优先排序」，用户明确否掉——「为什么要缩小帮助范围」。**最终规则：未绑定车次 → 空列表；已绑定 → 同车次全部可见，按 `createdAt` 倒序。**

### 1.3 数据真实性（用户反复反馈「假数据」）

| 问题 | 根因 | 处理 |
|---|---|---|
| 编辑资料后再进去又是默认界面 | `data: { form: getInitialProfile() }` —— **小程序 `data` 字面量在模块加载时求值一次**，所有页面实例共享同一个快照 | 抽出 `EMPTY_FORM`，改在 `onLoad` 里 `setData` |
| 私信时间是假的（「30 分钟前」不变） | `getMessageList` 有两处 mock 回退：云端失败返回 `mockData.messages`；`chat.js` 用 `nextMessages.length ? next : messages` | 两处都删掉，新增 `normalizeMessage` + `formatMessageTime` 统一格式化时间 |
| 消息列表出现「热心大叔」「旅者小李」 | 列表为空时回退 `mockData.conversations` | 删除回退，补空状态 |
| 会话时间显示 `2026-11-06T04:48:22.483Z` | 云函数返回的 Date 经 JSON 序列化后是原始 ISO 串，页面直接渲染 | 复用 `formatMessageTime`（已从 `cloud-api` 导出） |

> **原则**：云开发已就绪时，任何列表失败都返回空列表 + 空状态，不回退演示数据。假数据会掩盖真实错误，让人误判「功能好了」。

### 1.4 身份显示

| 问题 | 根因 | 处理 |
|---|---|---|
| 黄小怡账号里，会话显示的是「黄小怡」而不是发消息的李大英 | `createOrGetConversation` 把 `peerName` 写死成 `post.publisherInfo.nickname`（发布者昵称）。`peerName` 语义是「对方」，但对**发布者本人**来说对方是发起者，所以发布者打开会话看到的是自己 | `getConversationList` 按 `participantIds` 找出**另一个人**的 openid，批量查 `users` 取最新昵称/头像/等级；`createOrGetConversation` 新增 `participantInfo` 按参与者分别存；老数据无需迁移即自动纠正 |
| 头像全是「旅」 | 微信 2022/10 起收回 `wx.getUserProfile`，头像昵称必须用户自己填 | 项目 `pages/profile-edit` 已实现（`open-type="chooseAvatar"` + `input type="nickname"`）。本批补：`createPost` 的 `publisherInfo` 增加 `avatarText`/`avatarUrl`，会话列表支持真实头像 |

### 1.5 未读红点

| 问题 | 根因 | 处理 |
|---|---|---|
| 看完消息，tabBar 红点不动 | 两层原因：① `markConversationRead` 用点路径 `` [`unreadMap.${openid}`]: 0 `` 更新，键名异常时**静默失效**；② 该函数返回**硬编码的 `unreadCount: 0`**，且前端从未在任何地方刷过角标 | ① 改为整体重写 `unreadMap` 对象；② 真实统计并返回总未读数；③ 新增 `utils/badge.js` 统一角标逻辑（tab 索引只维护一处）；④ 聊天页进会话即刷角标、`onShow` 补刷、轮询发现新消息自动已读；⑤ 首页 `onShow` 也校准 |

### 1.6 拉黑闭环（本批重点，含未验证部分）

| 问题 | 根因 | 处理 |
|---|---|---|
| 拉黑后无法再互动，没有取消入口 | 功能本身就不存在 | 新增 `unblockUser` 云函数：`blocks` 记录置 `inactive`（保留历史不物理删除）+ 会话状态恢复 `active` |
| 拉黑后会话从消息列表消失，**根本点不进去** | `getConversationList` 带 `status: _.neq('blocked')` | 去掉该过滤，改为列表打「已拉黑」灰标签并保留会话 |
| 拉黑后首页还能看到对方帖子 | 无此逻辑 | `getPosts` 在**数据库查询层**用 `db.command.nin(hiddenOpenids)` 排除（不是取回 20 条再 JS 筛——客户端单次查询上限 20 条，先取后筛会让一页只剩十几条） |
| 两人互相拉黑后单方取消，能绕过另一方 | `sendMessage` 只看 `conversations.status` | 增加 `blocks` 双向复查；查询异常时放行，避免名单故障堵死正常聊天 |
| 拉黑点击后消息发不出去，不知是成功还是坏了 | 前端 `sendText` 不检查返回值 | 检查 `result.ok === false`，按 `code` 提示；拉黑加二次确认；失败改 `showModal`（toast 会截断长文案） |

**帖子隐藏是双向的**（我拉黑的 + 拉黑我的）。单向隐藏时，被拉黑方仍能看到帖子、点进去私信，却因会话被阻断而发不出消息，正是用户之前遇到的困惑。

### 3.3 如果按钮还是不出现，按这个顺序查

**第 1 步：确认云函数真的部署了（最常见原因，占九成）**

在开发者工具里**右键**下列目录 → 「上传并部署：云端安装依赖」：

| 云函数 | 不部署的后果 |
|---|---|
| `getMessageList` | **取消拉黑按钮不出现**（本问题的核心） |
| `blockUser` | 会话上不会记录 `blockedBy` |
| `unblockUser` | 新函数，没有它点了会弹「未就绪」 |
| `getBlockList` | 首页不会隐藏被拉黑者的帖子 |

> 部署完必须**重新编译**并**重新进入聊天页**。云函数更新不会自动推到已打开的页面。

**第 2 步：看聊天页顶部有没有黄色提示条**

如果出现「云函数 getMessageList 尚未更新到最新版本…」，说明第 1 步没做到位。这条提示是 `cloud-api.getChatState()` 检测到返回值里没有 `blocked` 字段时打的，专门用来区分「没部署」和「没做」。

**第 3 步：直接用云开发控制台调云函数**

控制台 → 云函数 → `getMessageList` → 「测试」，参数填：

```json
{ "conversationId": "把 conversations 集合里那条会话的 _id 粘进来" }
```

期望返回（关键字段）：

```json
{
  "ok": true,
  "peer": { "openid": "...", "name": "黄小怡", "avatarText": "黄" },
  "blocked": true,
  "blockedBy": "李大英的openid",
  "blockedByMe": true,
  "blockedByPeer": false
}
```

- `blocked: false` → 去第 4 步查数据库
- `blocked: true` 但 `blockedByMe: false` → `blockedBy` 是对方，属正常（对方拉黑了你，不该给你按钮）
- 返回里根本没有 `blocked` 字段 → 云函数还是旧版，回第 1 步

> 注意：控制台「测试」不会自动带上调用者 openid，`cloud.getWXContext().OPENID` 会是空的。要验证真实身份，用真机 + 云函数日志更准。

**第 4 步：查数据库**

云开发控制台 → 数据库：

1. `conversations` 集合，找到那条会话，检查两个字段：
   - `status` 应为 `"blocked"`
   - `blockedBy` 应为李大英的 openid
2. `blocks` 集合，检查是否有 `blockerId = 李大英openid`、`targetId = 黄小怡openid`、`status = "active"` 的记录

若 `blocks` 集合**不存在**，`blockUser` 的 `add` 会抛错，拉黑本身就没成功。`docs/01-数据库集合配置清单.md` 里有 `blocks` 的定义，权限设「仅创建者可读写」。

**第 5 步：看云函数日志**

控制台 → 云函数 → `blockUser` / `getMessageList` → 「日志」，找报错。

### 3.4 已知的剩余风险点（如果上面全对但依然不显示）

1. **`conversationId` 为空**：从帖子详情进入时依赖 `createOrGetConversation` 返回 `conversationId`。若该函数是旧版或失败，`conversationId` 为空 → `getChatState` 直接返回空对象 → `blocked: false`。排查：在 `chat.js` 的 `initChat` 里打日志看 `conversationId` 是否有值。
2. **两个账号实际不是同一个会话**：A 从帖子进、B 从消息列表进，若 `createOrGetConversation` 的 `relatedId` 不一致，会生成两条会话。
3. **`users` 集合里对方没有记录**：`resolvePeer` 会退回 `participantInfo` 或「同车旅客」，不影响按钮，只影响名字。

## 十、本批踩坑记录（给下一个人的提醒）

1. **`data` 字面量只在模块加载时求值一次**。任何依赖存储/全局状态的初始值，必须放 `onLoad` 里 `setData`。
2. **`await wx.showModal(...)` 不可靠**。部分基础库不返回 `{confirm}` 结构，必须用 `success` 回调。项目里 5 处弹窗统一走回调式。
3. **客户端查询单次上限 20 条**。过滤条件要下推到数据库查询层（`where`），不要「取回来再 JS 筛」，否则分页会缺斤少两。
4. **云函数写入的记录没有 `_openid`**。前端不能按创建者直查，必须走云函数。
5. **状态判定要收敛到一个接口**。聊天页曾经为了判断拉黑方向，依赖「URL 参数 + 另一个云函数」，漏部署任何一个都表现为「功能没做」。现在统一由 `getMessageList` 返回。
6. **失败要说话**。静默失败是本项目最高频的问题来源：`sendText` 不看返回值、`showModal` 吞异常、点路径更新不生效、mock 数据掩盖查询错误——每一个都让用户误以为「功能没做」。
7. **不要在云开发就绪时回退演示数据**。宁可显示空状态，也不要让假数据掩盖真实错误。
